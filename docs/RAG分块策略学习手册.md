## 1. 为什么 RAG 需要分块

### 1.1 从一个问题开始

你有一本 300 页的员工手册，用户问："请假需要提前几天申请？"

最朴素的方案：把 300 页全塞给大模型（LLM），让它自己找答案。

**为什么不行？**

```
LLM 的上下文窗口（能一次读多少字）是有限的：

GPT-4o      →  128K tokens  ≈ 10 万汉字
DeepSeek-V3 →  128K tokens  ≈ 10 万汉字
Claude 3.5  →  200K tokens  ≈ 16 万汉字

一本普通员工手册 ≈ 3~5 万字    → 勉强塞得下
一个公司的全部制度文件 ≈ 数百万字 → 完全塞不下
```

除了塞不下，还有两个严重问题：

| 问题 | 说明 |
|------|------|
| **成本** | 每次提问都把整本书发给 LLM，按 token 收费，贵到不可接受 |
| **注意力稀释** | LLM 在超长文本里容易"走神"，关键信息被淹没，回答反而变差 |

### 1.2 RAG 的解法

RAG（Retrieval-Augmented Generation，检索增强生成）的核心思路：

```
第一步：把文档切成小块（分块/Chunking）
第二步：把每块变成向量存起来（Embedding）
第三步：用户提问时，只找出最相关的 3~5 块
第四步：把这 3~5 块 + 用户问题 一起喂给 LLM
```

这样每次 LLM 只需要读几百字，而不是整本书。

```
完整文档（10万字）
      ↓ 分块
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ...（200个块）
│块001│ │块002│ │块003│ │块004│ │块005│
└─────┘ └─────┘ └─────┘ └─────┘ └─────┘
      ↓ 用户提问后，找最相关的 5 块
            ┌─────┐ ┌─────┐ ┌─────┐
            │块018│ │块019│ │块053│  ← 只有这 3 块进了 LLM
            └─────┘ └─────┘ └─────┘
```

### 1.3 分块的本质是什么

**分块本质上是在回答两个问题：**

1. **在哪里切？**（切割点的选择）
2. **切多大？**（块的大小控制）

不同的分块策略，就是对这两个问题给出不同的答案。

## 2. 分块的核心矛盾

理解分块策略之前，必须先理解这个根本矛盾：

### 块太小的问题

```
原文: "员工每年享有15天带薪年假。工作满1年不足3年的享有5天，
       满3年不足10年的享有10天，满10年以上的享有15天。
       申请年假需提前3个工作日提交申请表..."

切成很小的块（每块50字）：
块A: "员工每年享有15天带薪年假。工作满1年"
块B: "不足3年的享有5天，满3年不足10年的"
块C: "享有10天，满10年以上的享有15天。"
块D: "申请年假需提前3个工作日提交申请表"
```

用户问"年假怎么申请"，命中块D，但块D没有年假天数信息，LLM 回答不完整。

### 块太大的问题

```
把整章"请假制度"（3000字）作为一块：

用户问"事假扣多少钱"，这块里有答案，但也混杂了：
- 年假规定
- 病假规定
- 婚假规定
- 产假规定
- 丧假规定
...

LLM 要在 3000 字里找 1 句话，注意力被稀释，回答质量下降。
```

### 矛盾总结

```
块越小 → 检索越精准，但上下文不够，LLM 回答不完整
块越大 → 上下文越完整，但检索不精准，LLM 注意力被稀释

最优分块 = 在"检索精准"和"上下文完整"之间找平衡点
```

## 3. 分块策略详解

### 策略一：固定大小分块（Fixed Size Chunking）

**最基础的方案**，按字符数硬切。

```
原文: AAAAAAAAAA BBBBBBBBBB CCCCCCCCCC DDDDDDDDDD EEEEEEEEEE
      ←── 512字 ──→←── 512字 ──→←── 512字 ──→
      块1           块2           块3
```

**加入重叠（Overlap）解决边界问题：**

```
块1: AAAAAAAAAA BBB           （512字）
块2:         BBBBBBBBB CCC    （512字，和块1重叠50字）
块3:                 CCCCCCC  （512字，和块2重叠50字）
```

重叠的作用：防止一句完整的话被切成两半，关键信息落在边界处丢失。

| 优点 | 缺点 |
|------|------|
| 实现最简单 | 不理解语义，可能在句子中间硬切 |
| 适用任何格式 | 块与文档结构无关 |
| 速度最快，成本最低 | 同一语义可能跨两个块 |

**适合场景**：快速原型、非结构化纯文本、对精度要求不高的场景。

---

### 策略二：递归字符分块（Recursive Character Splitting）

**固定大小的升级版**，不是强行按字数切，而是按优先级尝试自然边界：

```
优先级从高到低尝试分隔符：
1. \n\n（段落）   → 在段落边界切，最自然
2. \n（换行）     → 在行边界切
3. 。！？（句子）  → 在句子边界切
4. ，；（短语）    → 在短语边界切
5. 空格           → 在词边界切
6. 字符           → 实在没办法才硬切
```

**效果对比：**

```
固定大小（在"年"字后强切）：
块1: "员工每年享有15天带薪年"
块2: "假。申请需提前3天..."

递归字符分块（在句号后切）：
块1: "员工每年享有15天带薪年假。"
块2: "申请需提前3天提交申请表..."
```

| 优点 | 缺点 |
|------|------|
| 尽量在自然语言边界切割 | 仍然不理解语义 |
| 实现简单，性能好 | 块与文档逻辑结构无关 |
| **2026 年基准测试 69% 准确率，仍是默认首选** | 对复杂文档结构无感知 |

**适合场景**：通用默认方案，大多数情况下的起点。

---

### 策略三：结构感知分块（Structure-Aware Chunking）

**利用文档本身的结构信息来切割。**

不同格式有不同的结构信号：

```
Markdown:
# 第一章 总则        ← 一级标题，切一个大块
## 1.1 适用范围     ← 二级标题，切一个子块
内容...
## 1.2 基本原则
内容...
# 第二章 请假制度    ← 新的大块
...
```

```
Word (.docx):
"Heading 1"样式 → 一级标题 → 切割点
"Heading 2"样式 → 二级标题 → 切割点
"正文"样式      → 普通内容 → 追加到当前块
```

```
PDF:
页面边界 → 天然的切割点（每页一个基础 segment）
```

| 优点 | 缺点 |
|------|------|
| 块与文档逻辑结构对齐 | 依赖文档有清晰格式 |
| 检索时知道内容属于哪一章 | 没有格式的文档退化回固定大小 |
| 溯源精准（章节信息保留在 metadata） | PDF 提取文字质量参差不齐 |

**适合场景**：结构清晰的规章制度、技术文档、有章节的报告。

---

### 策略四：语义分块（Semantic Chunking）

**完全按语义相似性切割，不管字数和格式。**

```
原理：
句1 → Embedding → 向量A
句2 → Embedding → 向量B
句3 → Embedding → 向量C

计算相邻句子向量的"距离"：
A-B 距离小 → 语义相近 → 合并到同一块
B-C 距离大 → 语义跳跃 → 这里切割
```

```
示例：
"员工享有年假。"       ─┐
"年假天数按工龄计算。" ─┤ 语义相近，合并为一块
"申请需提前3天。"      ─┘
──────────── 语义跳跃 ────────────
"薪资按月发放。"       ─┐
"绩效奖金按季度结算。" ─┘ 合并为另一块
```

**2026 年重要发现（反直觉）**：语义分块准确率只有 **54%**，比递归字符分块（69%）还低。

原因：语义分块切出的块太小（平均 43 tokens），喂给 LLM 时上下文不够用，生成质量反而下降。

| 优点 | 缺点 |
|------|------|
| 块的语义最完整 | 建库时每句都要 Embedding，慢且贵 |
| 不依赖文档格式 | 切出的块往往太小 |
| | 单独使用实测效果不如递归分块 |

**适合场景**：与其他策略结合使用，不建议单独用。

---

### 策略五：父子块检索（Parent-Child / Small-to-Big）

**2026 年工程上性价比最高的方案。**

核心思想：**用小块检索，用大块生成。**

```
建库时存两份：

父块（512字）："第二章 请假制度：年假15天，申请提前3天，
               特殊情况报HR审批，病假需提交医院证明..."
    │
    ├─ 子块1（128字）："年假15天，申请提前3天"
    ├─ 子块2（128字）："特殊情况需HR审批"
    └─ 子块3（128字）："病假需提交医院证明"

向量化并存入 Qdrant 的是：子块1、子块2、子块3（小而精准）
PostgreSQL 里记录：子块 → 父块 的对应关系
```

```
检索时：
用户问"病假怎么处理" → 命中子块3（精准）
                     → 找到父块（完整上下文）
                     → 把父块喂给 LLM（完整回答）
```

| 优点 | 缺点 |
|------|------|
| 检索精准（小块） + 上下文完整（大块） | 存储量翻倍 |
| 兼顾了核心矛盾的两端 | 实现比单层复杂 |
| 工业界 RAG 首选 | 需要维护父子关系 |

**适合场景**：生产级 RAG，对精度要求高的场景。

---

### 策略六：上下文检索（Contextual Retrieval）

**Anthropic 2025 年提出，效果提升最显著的工程化方案。**

核心思想：**入库前给每个块加一句"定位说明"**，让向量更有辨识度。

```
原始块：
"特殊情况需提前报 HR 审批"
（这句话脱离上下文很模糊，向量也模糊）

加工后（调用 LLM 生成说明）：
"本段来自《员工手册》第二章第3节，
 描述请假的特殊情形处理规则。
 原文：特殊情况需提前报 HR 审批"
（向量明确了：这是关于请假特殊情况的规则）
```

**效果**：与混合检索结合，检索失败减少 **49%**；再加上 Rerank，可减少 **67%**。

| 优点 | 缺点 |
|------|------|
| 检索精度提升显著 | 建库时每块调一次 LLM，成本增加 |
| 在现有架构上叠加，无需改变检索方式 | 大批量文档时成本可观 |
| 对模糊查询效果特别好 | |

**适合场景**：高精度要求、文档量不是特别大、愿意花一些建库成本。

---

### 策略七：Late Chunking（晚期分块）

**2025 年从实验转入实用的新方案。**

核心矛盾：普通分块时，每个块是独立 Embedding 的，块与块之间互相不知道对方的存在。

```
普通方式：
块A → 单独 Embedding → 向量A（不知道块B的存在）
块B → 单独 Embedding → 向量B（不知道块A的存在）

块A里如果有"他"（指代上一块的人名），向量完全不知道"他"是谁
```

```
Late Chunking：
整篇文章 → 全文 Embedding（每个 token 都"看到"了全文）
         → 在 token 级别的向量上切块
         → 每个块的向量里包含了全文上下文信息
```

**实测效果**：在学术论文等跨引用多的文档上，nDCG 指标稳定提升。

| 优点 | 缺点 |
|------|------|
| 块向量包含全文上下文，语义更准确 | 需要支持长上下文的特定 Embedding 模型 |
| 对代词指代、交叉引用的处理更好 | 目前主要 jina-embeddings-v2 支持 |
| | 文档越长收益越大，短文档收益有限 |

**适合场景**：学术论文、法律文件、技术手册等跨引用频繁的长文档。

---

### 策略八：Agentic Chunking（智能体分块）

**2025 年 3 月开源，让 AI 自己决定怎么切。**

```
传统方式：人规定策略 → 所有文档用同一套规则

Agentic Chunking：
文档 → Agent 分析文档类型和结构
     → Agent 选择最合适的策略（可多种组合）
     → Agent 自动标注每块元数据
     → 输出高质量的块
```

适合企业级多格式混合文档（有的是 Word，有的是 PDF 扫描件，有的是网页）。

| 优点 | 缺点 |
|------|------|
| 自动适配不同文档类型 | 成本最高（每个文档都要 LLM 分析） |
| 无需人工设计规则 | 速度慢 |
| 可处理复杂异构文档 | 实现复杂度高 |

**适合场景**：文档类型复杂多样、对质量要求极高、愿意承担较高成本的企业场景。

---

### 策略九：TopoChunker（拓扑感知分块）

**2026 年 3 月最新方案**，双智能体架构。

```
Inspector Agent → 分析文档结构，路由到三条处理路径：
  ├─ 结构化规则路径（有清晰章节的文档）
  ├─ 语义流路径（叙述性文章）
  └─ VLM 视觉路径（含图表的 PDF）

Refiner Agent → 处理代词指代、孤立术语、跨块引用
```

实测生成准确率比上代最优方案提升 **8%**，同时 Token 消耗减少 **23.5%**。

**适合场景**：复杂异构文档，2026 年最前沿方案，生产成熟度仍在积累中。

---

### 策略十：Vision-Guided Chunking（视觉引导分块）

**2025 年 6 月提出，专门解决含图表 PDF 的问题。**

```
普通 PDF 解析的问题：
┌────────────────────┐
│  季度营收（万元）   │
│  Q1  Q2  Q3  Q4   │    pypdf 提取后 →  "季度营收万元Q1Q2Q3Q4
│  120 145 189 210  │                    120145189210产品线..."
│  产品线：硬件/软件 │    （表格变成乱码）
└────────────────────┘

Vision-Guided 处理：
用多模态大模型（如 Gemini 2.5 Pro）"看图"理解表格
→ "本季度营收：Q1=120万，Q2=145万，Q3=189万，Q4=210万，
   产品线分为硬件和软件"
→ 向量化后完全可以被检索到
```

RAG 准确率提升 **14%**，块数量增加约 5 倍（更细粒度）。

| 优点 | 缺点 |
|------|------|
| 真正理解 PDF 中的表格、图表 | 成本极高（每个 PDF 页都调多模态 LLM）|
| 对财务报告等复杂 PDF 效果显著 | 速度慢 |

**适合场景**：财务报告、含大量图表的技术文档、需要理解表格内容的场景。

## 5. 策略可以叠加吗

**可以，而且叠加是主流做法。** 各策略解决的是不同层面的问题，互相不冲突。

```
典型的生产级叠加方案：

第1层：结构感知分段（Parser）
       ↓  把文档按章节切成语义完整的大段
第2层：递归字符分块（Chunker）
       ↓  把大段按字数控制成合适大小的子块
第3层：上下文检索（入库前处理）
       ↓  给每个子块加"这是哪章哪节的什么内容"
第4层：父子块存储（存储设计）
       ↓  检索用小块，生成用大块
第5层：Rerank 精排（检索后处理）
       ↓  从 Top-20 里精排出 Top-5
```

**叠加时的基本原则**：

- 优先叠加收益大、成本低的（结构感知、递归字符）
- 验证现有方案的瓶颈后再叠加成本高的（上下文检索、父子块）
- 不要为了"用了更多策略"而叠加，要看实际指标提升

## 6. 2026 年工业界现状

### 最重要的反直觉发现

> **简单方案 > 复杂方案（大多数时候）**
>
> 递归字符分块（最简单）在 2026 年基准测试中以 69% 准确率，持续击败语义分块（54%）、LLM 分块等复杂方案。
>
> 原因：复杂方案切出的块太小，虽然检索精准，但 LLM 生成答案时上下文不够。

### 推荐的实施路线图

```
第一阶段（立刻可用）：
  递归字符分块 + 结构感知分段
  → 绝大多数场景够用，先跑起来

第二阶段（有具体指标后升级）：
  + 上下文检索（Contextual Retrieval）
  → 检索失败明显时考虑，收益大成本中等

第三阶段（精度要求高时升级）：
  + 父子块检索
  → 需要"既精准又完整"时上，工业级首选

高级阶段（特定场景）：
  Late Chunking   → 文档跨引用多、代词指代多
  Vision-Guided  → 大量含图表的 PDF
  Agentic        → 多格式混合、企业级复杂文档
```

### 关键参数推荐（2026年验证）

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| 块大小 | 256~512 tokens | 事实查询用256~512，分析性查询用512~1024 |
| 重叠 | 10~20%（约50字）| 2026年研究发现重叠超过20%收益递减 |
| 粗筛数量（Top-K）| 20 | 先召回20个候选 |
| 精排数量（Rerank后）| 5 | 再精排到5个喂给LLM |

## 7. 本项目的分块实现

### 当前使用的策略（已叠加三层）

```
文件
 ↓
【第一层：结构感知分段】← 各 Parser 负责
  Markdown → 仅按 H1/H2 切节（H3~H6 连同正文留在所属大节内），保留 section 信息
            并把「只剩标题」的超小段并入下一段（避免孤立标题成块）
  DOCX     → 按 Heading 样式切段，保留标题层级
  PDF      → 按页切段，保留页码信息
  TXT/HTML → 整文档一段（无结构信息）
 ↓
【第二层：句子感知分块】← Chunker 负责
  SentenceSplitter（LlamaIndex）
  优先级：段落（\n\n）→ 中英文标点（。！？；，.;）→ 字符
  默认：chunk_size=512，overlap=50
 ↓
【第三层：碎块合并】← Chunker._merge_small（通用，所有格式生效）
  <60 字的碎块（残留标题/短句）自动并入相邻块，再重编全局 chunk_idx
 ↓
Embedding → 向量数据库（Qdrant）
  注：DashScope 单批 ≤10 条（MAX_BATCH=10），分块过多时按批循环发送
```

> **踩坑记录**：早期 Markdown 解析按 `#{1,6}` 每级标题都切段，当「标题紧跟子标题、中间无正文」时（如 `## 二、为什么用RAG?` 紧跟 `### 2.1 …`），会切出只含一行标题的超小块。它信息量极低却因关键词高度匹配被排到第一，溯源点开只有一行标题。修复 = 第一层只切 H1/H2 + 第三层碎块合并双保险。改完分块逻辑需对旧文档**重新索引**（`POST /api/documents/reindex-all`）才生效。

### 每个块保存的 metadata

```json
{
  "filename": "员工手册.docx",
  "section": "第二章 请假制度",
  "level": 1,
  "chunk_idx": 18,
  "sub_chunk_idx": 2
}
```

这些信息在溯源时使用，用户看到的"来源"就来自这里。

### 配置项（backend/.env）

```dotenv
CHUNK_SIZE=512      # 每块目标 token 数（约几百中文字），可调小提高精度
CHUNK_OVERLAP=50    # 相邻块重叠 token 数
RETRIEVE_TOP_K=10   # 向量检索粗筛数量
RERANK_TOP_K=5      # Rerank 后精排数量
# 以上 LLM/检索参数也可在「设置页」运行时修改并写回 .env
```

## 8. 后续可升级的方向

按照推荐顺序：

### 升级一：上下文检索（中等难度，高收益）

入库时给每块调一次 LLM 生成说明：

```python
# 伪代码
context = llm.generate(f"""
文档：{document_title}
章节：{section_title}
请用一句话描述以下内容属于什么：
{chunk_text}
""")

final_chunk = f"{context}\n\n{chunk_text}"
# 存 final_chunk 的向量，而不是 chunk_text 的向量
```

### 升级二：父子块检索（中等难度，高收益）

修改入库流程：
1. 用大块（1024字）切父块，用小块（256字）切子块
2. 子块存入 Qdrant（用于检索）
3. 父子关系存入 PostgreSQL（子块 chunk 表加 `parent_chunk_id` 字段）
4. 检索到子块后，查出父块，把父块文本喂给 LLM

### 升级三：混合检索（BM25 + 向量）

当前只用向量检索（语义相似），加入 BM25（关键词匹配）后效果互补：

- 向量：能理解"年假"和"带薪假期"是一个意思
- BM25：精确匹配，"HR 审批"这样的专有名词不会被遗漏

两路结果用 Reciprocal Rank Fusion（RRF）合并。
